* What this file is

How each page-image witness used by this repo was obtained, trimmed,
mapped to printed pages, and OCR'd -- enough to rebuild =witnesses/=
from nothing, and to know what any file in it is evidence /of/.

Moved here from =globe-lineation-workshop= with the witness-page
pipeline (=doc/globe-lineation.org=). The Layout section below gives
the paths as they are now. Elsewhere, paths are the workshop's:
=witnesses/= is now =$GLOBE_WITNESSES=; =data/witnesses.toml=, the leaf
tables and =data/witness-offsets.tsv= are under =data/globe/=, and
=src/witnesses.py= is =src/globe/witnesses.py=. The witness-preparation
tools (=src/ocr*.py=, =binarize_page.py=, =prune_alto.py=,
=build_leaf_tables.py=, =running_head_audit.py=), =data/alto-low-gc-*.tsv=,
=data/head-audit-review.tsv=, the =doubleday_*= modules, every =reports/=
file cited here, and =doc/forum.org= stayed in the workshop, and are
cited at its tag.

This is a record of provenance and processing, not of decisions.
/Why/ a witness was chosen, kept or retired is argued in
=doc/forum.org=; this file points there rather than repeating it.

Two witnesses are in use:

| Witness  | Printing                      | Copy            | Images                    | OCR layers                    |
|----------+-------------------------------+-----------------+---------------------------+-------------------------------|
| Trent    | London: Macmillan, 1887       | Trent Univ.     | IA JP2, 8-bit, 1538x2395  | Kraken ALTO; IA djvu (ABBYY)  |

* Layout

The witnesses live outside any repository, under =$GLOBE_WITNESSES=
(default =../globe-witnesses/=; until the workshop is frozen they are
still at =globe-lineation-workshop/witnesses/=). The files the build
reads are pinned by sha256 in =data/globe/witness-manifest.tsv=. Small,
hand-verified derived data lives in =data/globe/= and is tracked.

#+BEGIN_EXAMPLE
  $GLOBE_WITNESSES/
    Trent/
      scans/          1,054 JP2, IA leaves 0017-1070, IA filenames unchanged
      ocr/kraken/     Kraken ALTO, one file per leaf
      ocr/kraken-full.tar.gz    Full alto files with Glyph data
      ocr/kraken-full.tar.gz.sha256  checksum
      ocr/djvu.xml    IA's text layer, whole volume
      metadata/       IA _meta.xml, _marc.xml, _files.xml, _page_numbers.json
    Michigan/
      scans/          1,054 JPEG, leaves 00000015-00001068, HathiTrust names unchanged
      ocr/kraken/     Kraken ALTO, one file per leaf
      ocr/kraken-full.tar.gz    Full alto files with Glyph data
      ocr/kraken-full.tar.gz.sha256  checksum
      metadata/       HathiTrust catalog record 000241315
  data/globe/
    witnesses.toml        the registry: where each witness's scans and OCR layers are
    witness-manifest.tsv  sha256 of every witness file the build reads, per play
    witness-offsets.tsv   offsets and exceptions per witness (running-head audit)
    leaves-trent.tsv      leaf -> printed page
    leaves-miun.tsv       leaf -> printed page
#+END_EXAMPLE

*No script names these paths.* They go through the registry
(=data/globe/witnesses.toml=), which =src/globe/witnesses.py= loads and validates: it
refuses to run if a path is missing or the scans, an OCR layer and the
leaf table disagree in count or membership. Code names a (witness, layer)
pair: =trent/djvu=, =trent/kraken=, =miun/kraken=. The leaf tables carry a
=basis= column (=audit=, =reviewed=, =offset=) saying where each row's
printed number comes from. Task: =doc/agenda.org= =#phase0/witness-registry=.

*Files keep their leaf names; they are never renamed to printed page
numbers.* Two reasons: the djvu layer is indexed internally by IA leaf
(=usemap="worksofwilliamsh0000shak_y3h8_0876.djvu"=), so renamed scans
would disagree with their own text layer; and the leaf-to-page mapping
is not a constant offset everywhere (see the Michigan transposition), so
it belongs in a table that can record exceptions, not in filenames that
cannot.

*The ALTO =<fileName>= paths predate this layout.* Every ALTO file
records its source image as a repo-relative path from before the
reorganisation (e.g.
=witnesses/Trent/worksofwilliamsh0000shak_y3h8_jp2/..._0667.jp2=,
=witnesses/Michigan/miun-aba6868-0001-001-1789678210/00000874.jpg=).
Resolve by basename. The files have not been rewritten to match, and
should not be silently: the path is part of what the run recorded.

** OCR layer 1: IA djvu (ABBYY FineReader)
=ocr/djvu.xml= is IA's own text layer for the whole volume, front
matter included, indexed by IA leaf. IA's metadata gives the engine as
*ABBYY FineReader 11.0 (Extended OCR)*, converted with
=abbyy-to-hocr 1.1.7=. Not produced here; not modified.

Retained as a cross-check on the Kraken layer: it reads the same pixels
with a different engine and a different line segmentation. Known
behaviour on Lear p.860 (=reports/page-alignment-probe-lr-860-report.md=):
9 of 10 marginal numbers found, one (=140=, read =i4o=) only after
homoglyph correction, and =211= missed outright, split across two
word-boxes. djvu keeps a speaker prefix and its dialogue on one line,
so it produces no same-row split fragments.

** OCR layer 2: Kraken ALTO
Whole-volume run with =src/ocr-volume.py= (introduced =3956219=;
=--timeout= added =3f7cb83=), over the unmodified JP2s. Per page:

#+BEGIN_EXAMPLE
kraken -a -i <leaf>.jp2 <leaf>.xml segment -bl ocr -m catmus-print-fondue-large.mlmodel
#+END_EXAMPLE

| Setting      | Value                                                            |
|--------------+------------------------------------------------------------------|
| kraken       | 6.0.3 (from the ALTO =<Processing>= records)                     |
| Segmenter    | =blla.mlmodel= (kraken default), baseline mode                   |
| Recognizer   | CATMuS Print Fondue Large, DOI =10.5281/zenodo.10592716=         |
| Preprocessing| *none* -- no =binarize= step (but see the two exceptions below)  |
| Timeout      | 120 s per page (default)                                         |
| Output       | 1,054 ALTO v4 files, ~1.7 GB, ~73% of it =<Glyph>= elements      |

*Two pages were binarized before OCR.* Leaves *0667* (/Troilus and
Cressida/, printed 651) and *1043* (/Lucrece/, printed 1027): kraken's
baseline segmenter does not terminate on either original image (no
output after 240 s with recognition disabled, ~8.5 GB resident by 10
min). Ruled out: the timeout, JP2 decoding, resolution, the two-column
layout. Cause not established. Fixed by a local Sauvola threshold
(window 51, k 0.2) plus removal of 8-connected ink components under 6
px, via =src/binarize_page.py= at =3f7cb83=; global Otsu fixed 0667 but
not 1043. Recognition ran on the binarized PNG; coordinates are those of
the original scan (same 1538x2395 pixels). Each of the two files
records this in a =<Processing ID="BINARIZE_INPUT">= element in its own
=<Description>=, so the provenance travels with the file. Neither page is
in Lear or Antony; =tro= is a Group C play. Full account: =doc/agenda.org=
=#phase0/trent-bulk-ocr=.

* Pruning
=src/prune_alto.py= (added at =ca04812=) removes =<Glyph>= elements
(94% have =WIDTH="0"= and a degenerate polygon; their text is redundant
with the =String= =CONTENT=), keeps any glyph with GC below 0.9 in a
TSV sidecar, verifies each pruned file equals its source minus the
glyphs, and stamps a =<Processing ID="PRUNE_GLYPHS">= element naming the
commit. Other =<Processing>= elements, including =BINARIZE_INPUT=, are
kept. Full ALTO is the archive; pruned ALTO is what code reads.

*Status:* both witnesses pruned at =ca04812=. The stamp was checked on
Trent leaf 0667 only (which also keeps its =BINARIZE_INPUT= record);
that the rest are pruned is inferred from file sizes (largest 538 KB),

** Identity
/The complete works of William Shakespeare/, ed. W. G. Clark and W. Aldis
Wright, "arranged in their chronological order," Garden City, N.Y.: Nelson
Doubleday. A genuine two-volume book-club set -- *not* one book scanned
twice, an error in an earlier draft of this section. Both volumes print
the whole set's table of contents in their own front matter (normal for a
multi-volume set), but each volume's body holds only its own half. Two
columns; running heads give the play title and a sequential printed page
number (1-1075ish); marginal Globe-style line numbers are printed, set
flush-right within the column at the end of a line rather than in a true
margin gutter. King Lear is in Volume Two: printed pages 758-791
(Introduction 758, dramatis personae 759, Act I opens on 759-760).

Confirmed against the Tufts Tisch Library catalog (Cliff): OCLC 08687211
matches this edition exactly -- "Garden City, New York: Nelson Doubleday",
2 volumes, 22cm, "with an introd. to each play adapted from the
Shakespearean primer of Professor Dowden" (word for word against Volume
Two's scanned title page) -- but gives no year (=Creation Date: 19--=). A
second, related OCLC record (11438984, "Programmed Classics series",
publisher not identified) indicates this edition was reissued more than
once under different branding.

*The two volumes may not be the same printing.* Per Cliff, reading the IA
item pages directly: Volume One (=bwb_KT-315-451_1=) is dated 1950;
Volume Two (=bwb_S0-ATQ-198=, the one with Lear) is dated 1893. Neither
figure is independently confirmed here -- IA's own metadata API is
self-contradictory (1950 for Volume One, but an impossible "1853" for
Volume Two -- Nelson Doubleday did not exist in 1853), and no date is
printed anywhere in Volume Two's scanned front matter (checked: title
page, its verso, surrounding leaves). If Volume Two does preserve an
1893-vintage typesetting under later Doubleday branding, that would put
it much closer in age to Trent (1887) than to a 1950s reprint -- a live
hypothesis for the word-choice findings in
=reports/doubleday-comparison.md= =#2=, not one this investigation tested.

Same title-page boilerplate ("arranged in their chronological order") that
=doc/background.org= records as a since-corrected misattribution to Trent
-- the phrase belongs to this book, not that one.
